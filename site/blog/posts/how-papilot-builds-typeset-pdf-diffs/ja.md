コーディングエージェントに 2 ページにわたる数学の証明を引き締めてもらったり、LaTeX 原稿全体の記法を統一してもらったりすると、生の `git diff` は数秒で返ってきます。本当に神経をすり減らすのは、そのパッチを開いてからです。独自マクロの名前変更や段落の折り返し調整、あるいは `\begin{aligned}` ブロックの微修正だけでも、画面には赤と緑のバックスラッシュが何十行も並びます。プロジェクト全体に `latexdiff` をかけたとしても、壊れやすい数式環境や図表マクロでエラーが出たり、後続の改ページ位置がずれたりしがちで、「第 2 段落は承認し、式 (4) は却下して、選んだ変更だけをきれいに `.tex` ソースへ書き戻す」といった操作は望めません。

[Papilot](https://github.com/PapilotAI/papilot) がコンパイル済み PDF を真の主作業領域にするためには、組版レベルの比較がビルド終盤の重たいバッチ書き出しのように感じられてはなりません。エージェントによる各ラウンドの編集は作業ツリーから安全に隔離され、ローカルの単一インクリメンタル `latexmk` パスとほぼ変わらない時間でコンパイルされ、ページ上のハイライトが個々の注釈へ正確に紐づき、承認・却下のあらゆる判断が取り消し可能なレビュージャーナルに記録される必要があります。ここでは、そのレビューパイプラインが裏側でどのように動いているのかを解説します。

## Git ワークツリーと高速スナップショットでエージェントの各ターンを隔離する

速度よりもまず優先されるのは、原稿の安全境界です。PDF ページ上で文をハイライトしたり数式を枠で囲んだりして Codex、Claude、Cursor、または内蔵の Papilot Writer に注釈を送っても、エージェントがあなたの作業ディレクトリを直接書き換えることは決してありません。各タスクは、そのタスク専用の使い捨て Git ワークツリーの中でソースを編集します。

新旧のリビジョン比較を厳密に再現可能にし、クリックジャンプを支える SyncTeX が常に表示中の正確なソースバージョンを指すようにするため、すべてのビルドは元のフォルダを上書きするのではなく、それぞれ独立した不変（イミュータブル）のビルドディレクトリで実行されます。ただし、数百ページ規模の学位論文でビルドのたびにリポジトリ全体を Git にハッシュ計算させていては、スナップショットを作るだけでボトルネックになってしまいます。Papilot は専用の非公開 Git インデックス（原稿側は `.git/papilot/working-index`、各タスクのワークツリー側は `papilot/snapshot-index`）を介してスナップショットを記録し、直前のスナップショットやリポジトリのインデックスを起点にすることで、ファイルサイズや更新時刻が実際に変わったファイルだけを再ハッシュします。

![4段階のエンジニアリングパイプライン図：Git ワークツリースナップショット、シード状態を用いた章単位の差分ビルド、組版差分の帰属特定、取り消し可能なレビュージャーナル。](/assets/blog/review-pipeline.ja.svg "エージェントの各ターンは隔離された Git ワークツリーで実行され、ウォーム状態の LaTeX キャッシュを再利用して変更章を並列ビルドし、きめ細かな本文とアトミックな数式の差分を特定して、作業ツリーに触れる前に判断履歴を記録します。")

## 不変・隔離された LaTeX ビルドをフルリビルドではなく数秒に抑える

複数章からなる論文や 300 ページの学位論文に対してゼロから `pdflatex` や `xelatex` を走らせると、引用、相互参照、`minted` や TikZ のキャッシュを解決するために何度もパスを回す必要があります。ビルドを別ディレクトリに隔離する以上、単純に毎回空のフォルダを作って一からコンパイルしていては、`latexmk` が持つ貴重な差分ビルドの状態をすべて捨てることになってしまいます。

Papilot は 4 つの仕組みによって、隔離ビルドのオーバーヘッドを約 1 秒規模に抑えています。

1. **最も近い直近ビルドのクローン。** 新しいビルドフォルダを準備する際、同じ章セットを対象とした直近の完了済みビルドを調べ、Git ツリー上の差分ファイル数が最も少ない候補を起点に選びます。APFS を採用した macOS では、`cp -c` によるコピーオンライト（copy-on-write）でビルドディレクトリ全体を一瞬で複製し、変更されたファイルだけを Git からストリーム展開します。
2. **SyncTeX のインプレース書き換えと補助状態の引き継ぎ。** `latexmk` の依存関係データベース `.fdb_latexmk`、`.aux` や `.bbl` などの補助ファイル、そして `minted` キャッシュは複製先へそのまま引き継がれます。各ビルドフォルダには等長のディレクトリキーが割り当てられているため、Papilot は保持された SyncTeX データやログ内のパス接頭辞をバイトオフセットを壊さずにその場で書き換えられます。その結果、`latexmk` は通常 1 回の差分パスだけで済み、入力に変化がなければ再実行すら不要になります。
3. **シードビルドを用いた `\includeonly` による章単位の並列比較。** 複数ファイルで構成された原稿のうち 1〜2 章だけをエージェントが編集した場合、レビュービルドは本全体を再コンパイルしません。完全なベースビルド（シード）の `.aux` ファイルを土台として、変更前と変更後の双方が `\includeonly` で編集された章だけを並列コンパイルします。これにより未編集の章からの相互参照や図番号、文献引用の正確さを保ちつつ、共通のビルド時刻を固定することで、深夜 0 時をまたいでも `\today` による見せかけの差分が生じないようにしています。
4. **初回パス完了時の即時プレビューとクリーン環境への自動フォールバック。** 編集によってページ割りや引用が動き、`latexmk` が追加パスを予定した場合でも、パスフックが 1 回目の TeX パス直後に新しい組版ページと SyncTeX マップを画面へ反映し、残りの番号確定パスはバックグラウンドで完了させます。万が一、引き継いだ補助ファイルが原因で生成ファイル内にエラーが起きた場合は、自動的にクリーンなディレクトリから一度だけ再試行します。

| ビルド・レビュー工程 | 単純なクリーンビルド方式 | Papilot のインクリメンタル・レビューパイプライン |
| --- | --- | --- |
| 作業領域の隔離方式 | 作業フォルダを直接書き換えるか、全ファイルを毎回ゼロからコピー | タスク単位の Git ワークツリー + 専用差分インデックス（`working-index` / `snapshot-index`）、APFS 上では `cp -c` で複製 |
| 複数章原稿のレビューコンパイル | 変更前後それぞれで文書全体のマルチパス再ビルドを実行 | ベースビルドの `.aux` 状態を継承し、日時を固定した並列 `\includeonly` 差分ビルドを実行 |
| SyncTeX と補助ファイル状態 | 隔離ディレクトリごとにゼロから再生成 | 等長ビルドキーにより SyncTeX パスをインプレースで書き換え、`latexmk` のキャッシュ状態を再利用 |
| マルチパス実行時の体感待ち時間 | BibTeX とすべての相互参照パスが終わるまで画面更新を待機 | 1 パス目完了直後に PDF ページを更新表示し、残りのパスは裏で番号を収束 |

## きめ細かな本文オフセット帰属とアトミックな数式比較

変更前と変更後の PDF がコンパイルできても、2 ページ全体をただ左右に並べるだけでは十分ではありません。著者が求めているのは、論文本来の行間や組版コンテキストを失うことなく、紙面上のその場で論理的な変更ごとに採否を判断することです。

Papilot は「**分割できる地の文**」と「**一体のまま保つべき組版構造**」を明確に区別しています。

- **本文のきめ細かなソースオフセット。** 通常の段落内では、各編集が基底 `.tex` ソースの正確な文字オフセット範囲へと対応付けられ、レンダリングされた PDF 上で個別に帰属付けられたハイライトマークとして表示されます。`.tex` ファイル内の不可視な空白や改行位置だけの調整は同じ段落内の最も近い実質的な編集へ自動的にまとめられるため、意味のない整形ノイズを一つずつクリックして捌く必要はありません。
- **数式や図表のアトミックな保護。** ディスプレイ数式、表、図、参考文献エントリは分割不可能なアトミック単位として扱われ、紙面上で重なり合う PDF 領域は前後の行を残した単一の比較ブロックへと統合されます。これにより、実際の改行位置、カーニング、数式のスペーシングがそのまま保たれます。

![コンパイル済み PDF 上で数式が枠で囲まれ、文がハイライトされ、それぞれにエージェントへ送る著者の注釈が添えられている Papilot の画面スクリーンショット。](/assets/blog/notes.en.png "PDF 上の注釈が特定の引用箇所や数式領域をソースオフセットへ結びつけるため、一度に 1 件の注釈に絞ってレビューを進められます。")

タスクに PDF 注釈を添付した場合、Papilot は同じターンの中でメインの修正案とあわせて簡潔な**注釈ごとの代替案**も用意するよう接続先のエージェントに依頼できます。レビュー画面が開く前に、各代替パッチがその注釈に紐づくソース範囲内に厳密に収まっているかを検証し、隔離環境で候補プレビューを事前コンパイルします。注釈をクリックすればその注釈に対応するハイライトだけに紙面の焦点を絞ることができ、ローカルキャッシュから用意された言い回し候補を瞬時に切り替えたり、正確な `.tex` の diff 表示をトグルしたりできます——**レビュー中に追加の LLM 呼び出しは一切発生しません**。

## `main` に触れる前の取り消し可能なレビュージャーナル

ソース中心のエディタでは、AI チャットパネルで「保持」をクリックした瞬間に作業ファイルが書き換わってしまいます。Papilot では、「レビューの判断」と「ディスクへの反映」を意図的に切り離しています。

変更全体を承認する操作も、特定の注釈に対して代替案を選ぶ操作も、まずはタスク内の取り消し可能なレビュージャーナル（undoable review journal）に記録されるだけです。ある注釈を却下すれば、同じジャーナルを通じて該当する元の `.tex` ソース範囲だけが即座に復元され、同じ段落内の他の編集や判断には影響しません。すべての確認を終えて初めて、承認済みの変更をコミットせずに作業ディレクトリへ「**適用**」（Apply）するか（リンク済みであれば約 1 秒で Overleaf 上の共著者へ同期されます）、あるいはこのタスクの承認分だけを原稿の現在のブランチへ直接「**コミット**」（Commit）するかをあなた自身が選べます。

ブラウザ上でそのまま動く[静的なオンラインデモ](/demo/)を使えば、注釈ごとの組版比較、用意されたタスクのリプレイ、ローカル Git ステージングを今すぐ試すことができます。レビューエンジン、コンパイルパイプライン、デスクトップアプリケーションはすべて MIT ライセンスのオープンソースとして公開されています。コードの閲覧や Issue の起票、そして開発を応援する [GitHub でのスター](https://github.com/PapilotAI/papilot)をぜひお待ちしています。
