Chiedi a un agente di programmazione di asciugare una dimostrazione di due pagine o di uniformare la notazione lungo un intero manoscritto LaTeX, e il suo `git diff` grezzo arriverà in pochi secondi. È leggendo quel diff che comincia il vero ritardo. Una singola macro rinominata, un paragrafo mandato a capo diversamente o un blocco `\begin{aligned}` ritoccato si trasformano in decine di righe di codice sorgente rosse e verdi. Anche lanciando `latexdiff` sull'intero progetto, gli ambienti matematici in display più delicati spesso si rompono, le interruzioni di pagina slittano a valle e continua a mancare un modo pulito per accettare il secondo paragrafo, rifiutare la quarta equazione e scrivere su disco soltanto le modifiche al sorgente che hai scelto.

Perché [Papilot](https://github.com/PapilotAI/papilot) possa fare del PDF compilato lo spazio di lavoro principale, i confronti tipografici non possono dare la sensazione di una lenta esportazione batch a fine build. Ogni ciclo di modifiche dell'agente deve restare isolato dal tuo albero di lavoro, compilarsi all'incirca nel tempo di un singolo passaggio incrementale di `latexmk`, attribuire con precisione le evidenziazioni alle singole note e annotare ogni decisione di accettazione o rifiuto in un registro di revisione annullabile. Ecco come funziona questa pipeline dietro le quinte.

## Isolare i turni dell'agente in worktree Git e snapshot rapidi dell'albero

La sicurezza viene prima della velocità. Quando evidenzi frasi o riquadri equazioni su una pagina PDF e le invii a Codex, Claude, Cursor o Papilot Writer, l'agente non modifica mai direttamente la directory di lavoro del tuo manoscritto. Ogni attività viene invece eseguita all'interno di un proprio worktree Git usa e getta.

Per confrontare le revisioni in modo riproducibile — e garantire che SyncTeX punti sempre all'esatta versione del sorgente mostrata a schermo — ogni compilazione avviene in una directory di build immutabile anziché alterare sul posto la cartella dell'autore. Creare da zero uno snapshot di build su una tesi corposa diventerebbe facilmente un collo di bottiglia se Git dovesse ricalcolare l'hash dell'intero repository a ogni passaggio. Papilot lo evita registrando gli snapshot tramite indici Git privati dedicati (`.git/papilot/working-index` per il manoscritto e `papilot/snapshot-index` nel worktree di ciascun compito), inizializzato a partire dallo snapshot precedente o dall'indice del repository così che Git ricalcoli l'hash solo dei file la cui dimensione o data di modifica è effettivamente cambiata.

![Schema della pipeline ingegneristica in quattro fasi: snapshot su worktree Git, build incrementali dei capitoli su stato di base, attribuzione dei diff impaginati e registro di revisione annullabile.](/assets/blog/review-pipeline.it.svg "Ogni turno dell'agente gira in un worktree Git isolato, riutilizza lo stato caldo di LaTeX per compilare i capitoli in parallelo, attribuisce diff granulari per la prosa e atomici per le formule e salva decisioni annullabili prima di toccare il tuo albero di lavoro.")

## Far costare pochi secondi alle build LaTeX immutabili, anziché ricompilare da zero

Eseguire `pdflatex` o `xelatex` da zero su un articolo suddiviso in più capitoli o su una tesi di 300 pagine richiede molteplici passaggi per risolvere citazioni, riferimenti incrociati e cache di `minted` o TikZ. Poiché Papilot isola le compilazioni in directory distinte, un isolamento ingenuo getterebbe via a ogni turno tutto lo stato incrementale di `latexmk`.

Papilot mantiene rapide le compilazioni isolate grazie a quattro meccanismi:

1. **Clonazione della build recente più vicina.** Quando prepara una nuova cartella di compilazione, Papilot esamina le build completate di recente sullo stesso insieme di capitoli e sceglie la candidata il cui albero Git differisce per il minor numero di file. Su macOS con APFS, il copy-on-write di `cp -c` clona l'intera directory di build in un solo passaggio e poi trasferisce da Git unicamente i blob modificati.
2. **Riutilizzo dello stato ausiliario e riscrittura sul posto di SyncTeX.** Il database `.fdb_latexmk` di `latexmk`, i file `.aux` e `.bbl` e le cache di `minted` vengono trasferiti nella directory clonata. Poiché le cartelle di build usano chiavi di uguale lunghezza, Papilot riscrive sul posto i percorsi all'interno dei log e dei dati SyncTeX conservati senza invalidare gli offset di byte: così `latexmk` esegue di norma un solo passaggio incrementale, oppure nessuno quando gli input non sono cambiati.
3. **Compilazione parallela dei capitoli con `\includeonly` durante le revisioni.** Quando un agente modifica uno o due capitoli di un manoscritto multi-file, un ciclo di revisione non ricompila l'intero volume. Sia la versione di base sia quella rivista compilano in parallelo soltanto i capitoli toccati tramite `\includeonly`, alimentati dai file `.aux` di una build di base completa affinché riferimenti incrociati, numerazione delle figure e citazioni dei capitoli rimasti intatti restino esatti. Entrambe le build fissano inoltre un timestamp condiviso, così `\today` non genera mai diff fantasma a cavallo della mezzanotte.
4. **Anteprime dopo il primo passaggio e fallback pulito automatico.** Quando una modifica cambia l'impaginazione o le citazioni e `latexmk` pianifica passaggi aggiuntivi, un hook espone le pagine appena composte e la mappa SyncTeX subito dopo il primo passaggio, mentre la numerazione dei riferimenti finisce di assestarsi in background. Se uno stato ausiliario residuo dovesse mai provocare un errore nei file generati, Papilot riprova automaticamente una volta partendo da una directory pulita.

| Fase di build e revisione | Pipeline ingenua a build pulita | Pipeline incrementale di revisione di Papilot |
| --- | --- | --- |
| Isolamento dello spazio di lavoro | Modifica la cartella di lavoro o ricopia ogni file da zero | Worktree Git per singolo compito + indici privati di snapshot (`working-index` / `snapshot-index`), clonati con `cp -c` su APFS |
| Compilazione di revisione multi-capitolo | Ricompilazione completa multi-passaggio prima e dopo | Build parallele con `\includeonly` inizializzate coi file ausiliari della build di base e data bloccata |
| SyncTeX e stato ausiliario | Ricostruiti da zero per ogni directory isolata | Chiavi di build di uguale lunghezza consentono la riscrittura sul posto dei percorsi SyncTeX e il riuso dello stato di `latexmk` |
| Latenza multi-passaggio a schermo | Attende il termine di tutti i passaggi BibTeX e dei riferimenti incrociati | Mostra le pagine PDF aggiornate subito dopo il primo passaggio mentre i successivi consolidano la numerazione |

## Attribuzione granulare per la prosa e confronti atomici per la matematica

Una volta compilati il PDF di base e quello rivisto, affiancare due pagine intere non è ancora sufficiente: chi scrive vuole decidere su ciascuna modifica logica nel punto esatto in cui siede sulla pagina, senza perdere il contesto tipografico.

Papilot distingue **ciò che può essere suddiviso** da **ciò che deve restare intero**:

- **Offset granulari nella prosa.** All'interno dei normali paragrafi, ogni intervento corrisponde a precisi offset di caratteri nel sorgente `.tex` e a evidenziazioni attribuite separatamente sul PDF renderizzato. Gli aggiustamenti invisibili di spazi bianchi o ritorni a capo nel file `.tex` vengono raggruppati automaticamente con la modifica sostanziale più vicina nello stesso paragrafo, evitando all'autore di dover fare clic sul rumore di formattazione.
- **Costrutti TeX atomici.** Equazioni in display, tabelle, figure e voci bibliografiche restano unità atomiche, e le regioni PDF sovrapposte si fondono in un unico blocco di confronto coerente che mantiene ferme le righe circostanti — preservando a capo reali, crenatura e spaziatura matematica.

![Interfaccia di Papilot che mostra un'equazione riquadrata e una frase evidenziata sul PDF compilato, ciascuna corredata da una nota dell'autore pronta per l'agente.](/assets/blog/notes.en.png "Le note sul PDF collegano citazioni specifiche e regioni di equazioni agli offset del sorgente, così la revisione può concentrarsi su una nota alla volta.")

Quando alleghi note PDF a un compito, Papilot può anche chiedere all'agente collegato di preparare nello stesso turno **alternative concise per singola nota** accanto alla proposta principale. Prima di aprire la revisione, Papilot convalida ogni patch alternativa rispetto agli esatti intervalli di sorgente associati a quella nota e compila in isolamento le anteprime candidate. Facendo clic su una nota vengono messe a fuoco sulla pagina solo le evidenziazioni relative e puoi passare da una formulazione preparata all'altra — o attivare il diff `.tex` esatto — dalla cache locale, con **zero chiamate LLM aggiuntive** durante la revisione.

## Un registro di revisione annullabile prima che qualcosa tocchi `main`

Negli editor centrati sul sorgente, fare clic su "Mantieni" nel riquadro della chat IA altera immediatamente i tuoi file di lavoro. In Papilot, revisione e consegna sono deliberatamente separate.

Accettare una modifica — o scegliere un'alternativa per una singola nota — scrive in un registro di revisione annullabile interno al compito. Rifiutare una nota ripristina all'istante gli intervalli originali nel sorgente `.tex`, lasciando intatte le modifiche e le decisioni non correlate. Solo al termine della revisione scegli se premere **Applica** per riportare le modifiche approvate nella directory di lavoro senza creare commit (e, se collegata, sincronizzarle in circa un secondo con i coautori su Overleaf) oppure eseguire il **Commit** delle sole modifiche accettate in questo compito direttamente sul branch corrente del manoscritto.

Puoi mettere alla prova direttamente nel browser i confronti tipografici per singola nota, le riproduzioni di attività pronte e lo staging Git locale con la [demo statica online](/demo/). L'intero motore di revisione, la pipeline di compilazione e l'applicazione desktop sono open source con licenza MIT: esplora il codice, apri una issue o [lascia una stella a Papilot su GitHub](https://github.com/PapilotAI/papilot).
