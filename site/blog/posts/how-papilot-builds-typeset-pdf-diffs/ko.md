코딩 에이전트에게 두 페이지 분량의 수학 증명을 간결하게 다듬어 달라고 하거나 LaTeX 원고 전체의 표기를 통일해 달라고 요청하면, 몇 초 만에 날것의 `git diff`가 도착합니다. 진짜 피로가 시작되는 순간은 그 코드 패치를 열어 볼 때부터입니다. 사용자 정의 매크로 이름 하나를 바꾸거나, 영문 문단의 줄바꿈을 다시 정렬하거나, `\begin{aligned}` 수식 블록을 조금만 손보아도 화면에는 붉은색과 초록색 백슬래시가 수십 줄씩 펼쳐집니다. 프로젝트 전체에 `latexdiff`를 돌려 보더라도 복잡한 수식 환경이나 도표 매크로가 깨지고 뒤쪽 페이지 나눔이 전부 밀리기 일쑤이며, 무엇보다 "두 번째 문단은 수락하고 네 번째 수식은 거절한 뒤 선택한 수정만 깔끔하게 `.tex` 소스 파일에 반영하는" 방법은 제공되지 않습니다.

[Papilot](https://github.com/PapilotAI/papilot)이 컴파일된 PDF를 진정한 주 작업 공간으로 만들려면, 조판 수준의 비교 화면이 빌드 파이프라인 끝단에서 느리게 뽑아내는 일괄 내보내기처럼 느껴져서는 안 됩니다. 에이전트의 매 라운드 수정은 원본 작업 디렉터리로부터 안전하게 격리되어야 하고, 로컬에서 단일 증분 `latexmk` 패스를 돌리는 것과 비슷한 시간 안에 컴파일되어야 하며, 페이지 하이라이트가 개별 주석에 정확히 귀속되고 모든 '수락'과 '거절' 결정이 실행 취소 가능하고 추적 가능한 검토 저널에 기록되어야 합니다. 그 검토 파이프라인이 내부에서 어떻게 돌아가는지 살펴보겠습니다.

## Git 워크트리와 고속 스냅샷으로 에이전트의 매 수정 턴 격리하기

속도보다 앞서는 것은 원고의 안전 경계입니다. PDF 페이지 위에서 문장을 하이라이트하거나 수식을 박스로 감싸 Codex, Claude, Cursor 또는 내장된 Papilot Writer에 주석을 보내더라도, 에이전트는 저자가 읽고 있는 기본 작업 디렉터리를 절대 직접 건드리지 않습니다. 대신 각 작업은 해당 작업 전용으로 생성된 독립 Git 워크트리(worktree) 안에서 소스를 편집합니다.

수정 전후 판본 비교를 엄밀하게 재현하고 클릭 이동에 쓰이는 SyncTeX가 언제나 현재 화면에 표시된 바로 그 소스 버전을 가리키게 하려면, 모든 빌드는 원본 폴더를 제자리에서 덮어쓰는 대신 저마다 독립된 불변(immutable) 빌드 디렉터리에서 수행되어야 합니다. 하지만 수백 페이지에 달하는 학위논문에서 매 빌드마다 Git이 저장소 전체를 스캔해 해시를 다시 계산한다면 스냅샷을 준비하는 과정만으로도 병목이 생깁니다. 이를 피하기 위해 Papilot은 전용 비공개 Git 스냅샷 인덱스(원고 작업 트리는 `.git/papilot/working-index`, 각 작업 워크트리는 `papilot/snapshot-index`)를 통해 스냅샷을 기록합니다. 직전 스냅샷이나 저장소 인덱스를 시드로 삼기 때문에 Git은 파일 크기나 수정 시각이 실제로 바뀐 소스 파일만 다시 해시합니다.

![4단계 엔지니어링 파이프라인 구조도: Git 워크트리 스냅샷, 시드 기반 장 단위 증분 빌드, 조판 차분 귀속, 실행 취소 가능한 검토 저널.](/assets/blog/review-pipeline.ko.svg "에이전트의 매 작업 턴은 독립된 Git 워크트리에서 실행되며, 웜 상태의 LaTeX 캐시를 재사용해 변경된 장만 병렬 빌드하고, 세밀한 본문 및 원자적 수식 비교를 생성한 뒤 원본 작업 트리를 건드리기 전 검토 저널에 결정을 기록합니다.")

## 격리된 불변 LaTeX 빌드를 클린 리빌드가 아닌 초 단위로 단축하기

여러 장으로 구성된 논문이나 300페이지 분량의 학위논문에서 처음부터 `pdflatex`나 `xelatex`을 실행하면 인용, 상호 참조, 그리고 `minted`나 TikZ 캐시를 해결하기 위해 여러 차례 패스를 반복해야 합니다. 빌드를 별도 디렉터리에 격리한다고 해서 매번 빈 폴더를 새로 만들어 처음부터 컴파일한다면 `latexmk`가 지닌 가장 소중한 증분 빌드 상태를 통째로 버리게 됩니다.

Papilot은 네 가지 메커니즘을 통해 격리 빌드의 추가 오버헤드를 약 1초 수준으로 압축합니다.

1. **가장 가까운 최근 빌드 디렉터리 복제.** 새 빌드 폴더를 준비할 때 Papilot은 동일한 장(chapter) 집합에 대해 최근 완료된 빌드들을 살펴보고 Git 트리에서 바뀐 파일 수가 가장 적은 후보를 출발점으로 고릅니다. APFS 파일 시스템을 사용하는 macOS에서는 `cp -c` 쓰기 시 복사(copy-on-write)가 빌드 디렉터리 전체를 한 단계로 즉시 복제한 뒤, 실제로 변경된 블롭만 Git에서 스트리밍해 기록합니다.
2. **제자리 SyncTeX 경로 재작성 및 보조 캐시 승계.** `latexmk`의 의존성 데이터베이스 `.fdb_latexmk`, `.aux` 및 `.bbl` 보조 파일, 그리고 `minted` 캐시가 복제된 디렉터리로 그대로 이어집니다. 각 빌드 폴더는 동일한 길이의 디렉터리 키를 사용하므로 Papilot은 보존된 SyncTeX 데이터와 로그 안의 경로 접두사를 바이트 오프셋을 깨뜨리지 않고 제자리에서(in-place) 치환할 수 있습니다. 덕분에 `latexmk`는 대개 단 한 번의 증분 패스만 실행하며, 입력이 바뀌지 않았다면 아예 재실행조차 하지 않습니다.
3. **시드 빌드 기반 병렬 `\includeonly` 장 단위 비교.** 다중 파일 원고에서 에이전트가 한두 장만 수정했을 때 검토 빌드는 책 전체를 다시 컴파일하지 않습니다. 전체 베이스 빌드(시드)의 `.aux` 보조 파일을 밑바탕으로 삼아 수정 전과 수정 후 판본 모두 바뀐 장만 `\includeonly`로 동시에 병렬 컴파일합니다. 이를 통해 수정되지 않은 장의 상호 참조와 그림 번호, 참고문헌 인용을 정확히 유지하면서도 공통 빌드 타임스탬프를 고정해 자정을 넘길 때 `\today`가 가짜 차분을 만들어 내는 일을 방지합니다.
4. **1차 패스 즉시 미리보기와 클린 폴백 자동 전환.** 수정으로 인해 페이지 나눔이나 인용 번호가 바뀌어 `latexmk`가 추가 패스를 예약하더라도, 패스 훅이 첫 번째 TeX 컴파일 직후 새로 조판된 페이지와 SyncTeX 맵을 먼저 화면에 띄우고 나머지 번호 수렴 패스는 백그라운드에서 마무리합니다. 만약 이전 보조 파일 상태 때문에 생성 파일 내부에서 오류가 발생하면 시스템이 자동으로 깨끗한 디렉터리에서 한 번 재시도합니다.

| 빌드 및 검토 단계 | 단순 클린 빌드 파이프라인 | Papilot 증분 검토 파이프라인 |
| --- | --- | --- |
| 작업 공간 격리 방식 | 원본 작업 폴더를 직접 변경하거나 매번 전체 파일을 새로 복사 | 작업 단위 Git 워크트리 + 비공개 증분 스냅샷 인덱스(`working-index` / `snapshot-index`), APFS에서 `cp -c`로 복제 |
| 다중 장 원고 검토 컴파일 | 수정 전후 각각 문서 전체를 처음부터 멀티패스 재빌드 | 베이스 빌드 `.aux` 상태를 시드로 삼아 날짜를 고정한 병렬 `\includeonly` 증분 빌드 수행 |
| SyncTeX 및 보조 상태 | 격리 디렉터리마다 매번 처음부터 다시 생성 | 동일 길이 빌드 키로 SyncTeX 경로를 제자리 재작성하고 `latexmk` 캐시 상태를 재사용 |
| 멀티패스 대기 체감 시간 | BibTeX와 모든 상호 참조 패스가 끝날 때까지 화면 갱신 대기 | 1차 패스 완료 직후 새 PDF 페이지를 즉시 표시하고 후속 패스는 백그라운드에서 번호 수렴 |

## 세밀한 본문 오프셋 매핑과 원자적 수식 비교

수정 전과 수정 후의 두 PDF 페이지가 컴파일되었다고 해도, 두 페이지 전체를 그저 좌우로 나란히 띄워 놓는 것만으로는 충분하지 않습니다. 저자가 원하는 것은 논문 고유의 줄 간격과 조판 문맥을 잃지 않은 채 지면 위의 제자리에서 논리적 변경 사항 하나하나를 결정하는 일입니다.

Papilot은 차분을 귀속할 때 '**쪼갤 수 있는 산문**'과 '**온전히 유지해야 하는 조판 구조**'를 구분합니다.

- **본문의 세밀한 소스 오프셋.** 일반 산문 문단 안에서는 각 추가·삭제가 하부 `.tex` 소스의 정확한 문자 오프셋 구간에 매핑되며, 렌더링된 PDF 위에서 개별적으로 귀속된 하이라이트 표시를 생성합니다. `.tex` 파일 내의 보이지 않는 공백이나 단순 줄바꿈 재정렬은 같은 문단에서 가장 가까운 실질적 수정에 자동으로 묶이므로 의미 없는 서식 노이즈를 일일이 클릭하며 넘길 필요가 없습니다.
- **복잡한 수식과 도표의 원자적 보호.** 디스플레이 수식, 표, 그림, 참고문헌 항목은 쪼개지지 않는 원자적 단위로 유지되며, 지면 위에서 겹치거나 인접한 PDF 영역은 주변 문맥 줄을 포함한 하나의 일관된 비교 블록으로 병합되어 실제 줄바꿈과 커닝, 수식 간격을 온전히 보존합니다.

![컴파일된 PDF 위에서 수식 하나가 박스로 지정되고 문장 하나가 하이라이트되어 있으며, 각각 에이전트에게 전달할 저자 주석이 달린 Papilot 인터페이스 스크린샷.](/assets/blog/notes.en.png "PDF 주석이 특정 인용구와 수식 영역을 소스 오프셋 구간에 정확히 연결해 주어, 한 번에 주석 하나씩 초점을 맞춰 하이라이트와 대안을 검토할 수 있습니다.")

작업을 보낼 때 PDF 주석을 함께 첨부하면, Papilot은 연결된 에이전트에게 같은 턴 안에서 기본 수정안과 더불어 간결한 **주석별 대안 문구**도 함께 준비하도록 요청할 수 있습니다. 검토 화면이 열리기 전에 시스템은 각 대안 패치가 해당 주석에 연결된 소스 범위 안에 엄격히 들어오는지 검증하고 격리 환경에서 후보 미리보기를 미리 컴파일합니다. 특정 주석을 클릭하면 페이지 위에서 그 주석의 하이라이트만 집중 조명되며, 로컬 캐시에 준비된 여러 표현 대안과 정확한 `.tex` diff 보기를 즉시 오갈 수 있습니다. **검토 과정 전체가 로컬에서 이루어지므로 검토 중 추가 LLM 호출은 전혀 발생하지 않습니다.**

## 변경 사항이 `main`에 닿기 전: 실행 취소 가능한 검토 저널

소스 코드 중심 편집기에서는 AI 채팅 패널에서 '유지'를 누르는 즉시 작업 공간의 파일이 곧바로 덮어써집니다. 반면 Papilot에서는 '검토 판단'과 '디스크 반영'을 의도적으로 두 단계로 분리했습니다.

전체 변경을 수락하든 특정 주석에 대해 대안 문구를 선택하든, 그 결정은 먼저 작업 내부의 실행 취소 가능한 검토 저널(undoable review journal)에 기록될 뿐입니다. 어떤 주석을 거절하면 같은 저널을 통해 해당하는 원래 `.tex` 소스 구간만 즉시 복원되며 같은 문단 안의 다른 수정이나 결정은 그대로 유지됩니다. 모든 검토를 마친 뒤에야 비로소 승인된 변경 사항을 커밋 없이 작업 디렉터리에 '**적용**'(Apply)할지(동기화가 연결되어 있다면 약 1초 만에 Overleaf의 공저자에게 전달됩니다), 아니면 이 작업에서 수락한 수정만 원고의 현재 브랜치에 바로 '**커밋**'(Commit)할지 직접 선택하게 됩니다.

브라우저에서 바로 열 수 있는 [정적 온라인 데모](/demo/)를 통해 주석별 조판 비교와 준비된 작업 리플레이, 로컬 Git 스테이징을 설치 없이 테스트해 보실 수 있습니다. 전체 검토 엔진과 컴파일러 파이프라인, 데스크톱 애플리케이션은 모두 MIT 라이선스 오픈소스로 공개되어 있으니 [Papilot GitHub 저장소](https://github.com/PapilotAI/papilot)에서 코드를 살펴보거나 이슈를 남기고, 스타를 눌러 개발을 응원해 주세요.
