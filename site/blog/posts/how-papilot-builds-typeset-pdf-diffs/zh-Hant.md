請程式設計 AI 代理幫你收緊兩頁數學證明，或是統一整篇 LaTeX 論文裡的記號，往往幾秒鐘就能拿到一份 `git diff`。真正消耗心力的時候，反而是從打開這份程式碼修補檔開始的：改一個自訂巨集、重排一段英文換行，或者微調一組 `\begin{aligned}` 公式，都會在螢幕上鋪開幾十行紅綠交錯的反斜線。就算對整個專案跑一遍 `latexdiff`，複雜的數學環境與圖表巨集也常常報錯、把後文的分頁全部擠亂，更無法讓你優雅地「接受第二段、拒絕第四個公式」，再把選定的修改乾淨地寫回 `.tex` 原始檔。

[Papilot](https://github.com/PapilotAI/papilot) 想把編譯後的 PDF 變成真正的主工作區，排版級對比就絕不能像管線末端的批次匯出那樣遲緩。AI 代理的每一輪修改都必須與原稿工作目錄安全隔離，編譯耗時要接近本機單次增量 `latexmk`，頁面螢光標記要精準歸屬到每一則批註，而且每一次「接受」或「拒絕」都必須可復原、可追溯。下面分享這套審閱管線在底層是如何運轉的。

## 用 Git 工作樹與增量快照隔離每一次代理修改

在速度之前，首先是原稿的安全邊界。當你在 PDF 頁面上螢光標記句子或框出公式，把批註傳給 Codex、Claude、Cursor 或內建的 Papilot Writer 時，AI 代理永遠不會直接改動你正在閱讀的主工作目錄，而是在專屬於當前任務的獨立 Git 工作樹（worktree）中編輯原始碼。

為了保證新舊版本對比嚴格可重現——並且讓點擊跳轉所依賴的 SyncTeX 始終指向當前展示的那一版原始碼——每一次建置都必須在各自獨立的不可變建置目錄中完成，而不能在原資料夾裡原地覆寫。如果面對一部幾百頁的學位論文，每次建置都讓 Git 全量掃描並計算整個儲存庫的雜湊值，光準備快照就會拖慢節奏。為此，Papilot 使用獨立的私有 Git 快照索引（主工作區為 `.git/papilot/working-index`，任務工作樹內為 `papilot/snapshot-index`）記錄快照：每次以前一版快照或儲存庫既有索引為起點，Git 只需重新計算檔案大小或修改時間真正發生變化的原始檔雜湊。

![四階段工程管線示意圖：Git 工作樹快照、基於種子狀態的章節增量編譯、排版級差異歸屬，以及可復原審閱日誌。](/assets/blog/review-pipeline.zh-Hant.svg "每輪 AI 代理任務都在獨立 Git 工作樹中執行，重用熱快取並行編譯變動章節，完成細粒度內文與原子數學公式對比，並在真正套用回原稿前透過審閱日誌管理每項決定。")

## 讓隔離的不可變 LaTeX 建置像單次增量編譯一樣快

在一篇多章節長文或三百多頁的論文上從零執行 `pdflatex` 或 `xelatex`，往往要跑多輪才能結清交叉引用、參考文獻以及 `minted` 或 TikZ 快取。既然每次建置都在獨立目錄裡進行，如果單純建立空資料夾從頭編譯，就會把 `latexmk` 最寶貴的增量狀態全部丟棄。

Papilot 透過四項機制把隔離建置的額外開銷壓縮到約一秒量級：

1. **複製最接近的歷史建置目錄。** 準備新建置時，Papilot 會在相同章節集合的近期已完成建置中，挑選與新版本原始碼差異檔案最少的一份作為起點。在採用 APFS 檔案系統的 macOS 上，`cp -c` 寫入時複製（copy-on-write）能一步複製整個建置目錄，隨後只從 Git 串流寫入發生變動的少量檔案。
2. **原地重寫 SyncTeX 與保留輔助檔案快取。** `latexmk` 的 `.fdb_latexmk` 相依性資料庫、`.aux` 與 `.bbl` 輔助檔案以及 `minted` 快取都會隨複製一併繼承。由於各個建置目錄採用等長路徑鍵名，Papilot 可以直接在保留的 SyncTeX 資料與日誌裡原地替換路徑前綴，而不會破壞位元組偏移量——這樣 `latexmk` 通常只需跑一輪增量編譯，輸入未變時甚至無需重跑。
3. **基於種子建置的並行 `\includeonly` 章節對比。** 當代理只修改了多檔案論文中的一兩章時，審閱建置不會重編整本書，而是以完整基礎建置（seed）的 `.aux` 輔助檔案為底座，利用 `\includeonly` 同時並行編譯修改前後的變動章節，既保住了跨章引用、圖表編號與文獻引用的準確性，又固定了統一建置時間戳記，避免跨午夜時 `\today` 製造虛假差異。
4. **首輪預覽上屏與髒快取自動回退。** 當某次修改移動了頁碼或引用、`latexmk` 需要繼續跑後續輪次時，掛鉤會在第一輪 TeX 編譯結束後立即把新產生的頁面與 SyncTeX 映射呈現在視圖中，讓後續結清編號的輪次在背景完成；一旦舊輔助檔案引發錯誤，系統會自動回退到乾淨目錄重試一次。

| 建置與審閱環節 | 傳統全量重建或腳本拼接方案 | Papilot 增量審閱管線 |
| --- | --- | --- |
| 工作區隔離方式 | 直接改動原目錄，或每次全量拷貝所有專案檔案 | 任務級獨立 Git 工作樹 + 私有 Git 增量快照索引（`working-index` / `snapshot-index`），APFS 下透過 `cp -c` 複製 |
| 多章節論文審閱編譯 | 修改前後分別從頭跑多輪整書編譯 | 繼承種子建置 `.aux` 狀態，對變動章節並行執行 `\includeonly` 增量建置並鎖定日期 |
| SyncTeX 與輔助快取 | 新目錄每次從零產生 | 等長建置目錄鍵名支援原地重寫 SyncTeX 路徑，重用 `latexmk` 快取狀態 |
| 多輪編譯等待體驗 | 必須等 BibTeX 與全部交叉引用輪次徹底跑完才顯示頁面 | 首輪編譯完成即刻重新整理頁面預覽，後續輪次在背景收斂頁碼與引用編號 |

## 細粒度內文偏移映射與原子級公式對比

拿到修改前後的兩份編譯版面後，僅僅把兩整頁 PDF 左右並排放著依然不夠直觀——作者希望在論文原有的行距與上下文裡，逐條對每一處邏輯修改拍板。

Papilot 在差異歸屬上區分了「**可拆分的散文**」與「**必須保持完整的排版結構**」：

- **內文細粒度原始碼偏移。** 在一般內文段落裡，每一處增刪都精確映射到底層 `.tex` 檔案的字元偏移區間，並在算繪後的 PDF 上產生各自獨立的螢光標記；原始碼裡單純的空白或換行重排會自動併入同段最近的實質性修改中，避免審閱時被無意義的格式微調打擾。
- **複雜數學與圖表的原子保護。** 展示型公式、表格、插圖與參考文獻條目保持為不可拆碎的原子單元；頁面上相鄰重疊的裁切區域會合併為同一塊帶上下文的版面對比區塊，完整保留真實的字距、換行與數學公式間距。

![Papilot 介面截圖：在排版後的論文頁面上框選公式並標記句子，各自附有準備交給代理的作者批註。](/assets/blog/notes.en.png "頁面批註將引文與公式區域精確關聯到原始碼偏移區間，使審閱面板可以每次只聚焦單則批註的標記與備選方案。")

當你在傳送任務時附帶了 PDF 批註，Papilot 還可以在同一輪請求裡讓連接的代理一併準備簡明的**單則批註備選改法**。在審閱介面打開前，系統會先驗證每份候選修補檔是否嚴格落在對應批註關聯的原始碼區間內，並在隔離環境中預先編譯版面預覽。點擊某則批註即可在頁面上只聚焦該處修改，在本機快取的不同措辭方案與 `.tex` 原始碼 diff 視圖之間即時切換——**整個審閱過程完全在本機完成，不會再觸發任何額外的模型呼叫**。

## 在改動進入 `main` 主分支之前：可復原的審閱日誌

在以原始碼為中心的編輯器裡，點擊對話側欄的「保留」往往當場就會改寫你的工作區檔案。而在 Papilot 中，「審閱判斷」與「寫入交付」被刻意拆成了兩步。

無論是接受整處修改，還是為某則批註選定備選方案，都只是寫入當前任務的可復原審閱日誌（undoable review journal）；拒絕某則批註則會透過同一套日誌立即還原對應的原始 `.tex` 區段，而不影響同一段落裡的其他決定。直到全部過目完畢，才由你決定是點擊「**套用**」（Apply）將通過審閱的改動寫回工作目錄而不自動提交（若已連結同步，改動會在約 1 秒內送達合作者的 Overleaf 頁面），還是點擊「**提交**」（Commit）僅將此任務已接受的改動在當前分支上建立一筆乾淨提交。

你可以直接打開瀏覽器裡的[靜態互動展示](/demo/)，免安裝體驗按批註聚焦的排版對比、預設任務重播與本機 Git 暫存管理。Papilot 的審閱引擎、編譯管線與桌面應用程式全部依據 MIT 授權條款開源，歡迎前往 [GitHub 儲存庫](https://github.com/PapilotAI/papilot)閱讀原始碼、提交 Issue，或按一顆 Star 支持我們的開發。
