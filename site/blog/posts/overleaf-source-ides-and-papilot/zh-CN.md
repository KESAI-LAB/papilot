几乎每个用 LaTeX 写论文的团队，最终都会在工具上达成某种妥协：有人喜欢打开浏览器就能改稿、不必折腾几个 GB 的 TeX 发行版；有人习惯守在本地代码编辑器里，配合 Git、快捷键和编程智能体；还有人总要把编译好的 PDF 导出来放到平板或全屏阅读器里通读——因为只有面对真正排好版的页面，生硬的段落过渡、拥挤的三线表和悄然写错的上下标才会浮出水面。

今天大家搜索“AI 写 LaTeX 工具”时，缺的早已不是足够聪明的模型。主流编程智能体已经很擅长跨文件检索宏定义、整理 `.bib` 文献甚至重排公式。真正决定日常改稿质量的，是围绕智能体建立的**工作区契约**：你在哪里指出问题、拿什么核对 AI 改出来的结果，以及换用更顺手的工具时，会不会迫使合作者跟着迁移。

与其宣称某一款工具能替代一切，不如把当前最常见的三种 LaTeX 工作流放在一起客观对比——以 Overleaf 为代表的浏览器分屏编辑器、接入编程智能体的本地源码 IDE，以及 [Papilot](https://github.com/PapilotAI/papilot) 以成稿 PDF 为中心的工作区——看看它们各自擅长什么，又如何通过实时同步在同一篇手稿上无缝配合。

## 现有 LaTeX 工具各自做对了什么

在讨论“以源码为中心”的 AI 改稿瓶颈之前，值得先承认 Overleaf 与本地代码编辑器之所以成为主流，是因为它们切切实实解决了各自时代的痛点。

**Overleaf 解决了多人协作的准入门槛。** 在在线编辑器普及之前，跨校合作写一篇论文，往往还没动笔写摘要就要先帮合作者排查 TeX Live 年份差异、缺失的宏包和 Git 冲突。发一个链接就能在浏览器里同时打字、看到彼此的光标，至今仍是让不同技术背景的合作者零配置进入同一份稿件最省心的方式，尤其适合手头没有安装本地 TeX 环境的设备。

**本地源码 IDE 解决了工程规模与自动化。** 用 VS Code 配合 LaTeX Workshop，或是 Cursor、Neovim 加上 Claude Code、Codex 等命令行智能体，在本地 Git 仓库里工作，能获得极快的跨文件搜索、离线 `latexmk` 编译、脚本化图表生成，以及在编写 `.cls` 文档类、`.sty` 宏包或复杂底层 TikZ 宏时的精细源码控制力。

但这两种工作流在同一个环节遇到了明显阻力：**审阅 AI 对正文论证与数学推导所做的实质性修改**。

![三种 LaTeX 工作流并排对比：Overleaf 浏览器分屏、接入智能体的本地源码 IDE，以及支持与 Overleaf 实时同步的 Papilot PDF 工作区。](/assets/blog/three-workflows.zh-CN.svg "Overleaf 擅长零配置网页多人协作，源码 IDE 擅长底层标记编辑；Papilot 将 AI 批注与修改审阅移回渲染后的 PDF，并通过实时同步与 Overleaf 互通。")

无论在网页分屏还是代码 IDE 里，AI 助手修改的都是 `.tex` 源码，交回给作者审阅的也首先是红绿交错的代码 diff。面对跨行重排的英文长句，或是夹杂自定义宏的多行 `\begin{align}` 推导，看代码补丁意味着作者必须在脑海里“人肉编译” LaTeX；哪怕重新编译出整份新 PDF，它也不会主动标出第九页究竟改了哪几个符号，你依然要靠肉眼在新旧两版之间来回比对。

## 六个维度的客观工作流对比

下表从日常写作、AI 批注、改动审阅到多人协作，梳理了三种环境的真实差异：

| 对比维度 | Overleaf（网页在线编辑器） | 本地源码 IDE + 编程智能体（VS Code / Cursor / CLI） | Papilot（以成稿 PDF 为中心的智能体工作区） |
| --- | --- | --- | --- |
| 主工作区重心 | 左右分屏：左侧 `.tex` 代码编辑，右侧 PDF 预览 | `.tex` 目录树与代码窗格为主，PDF 仅作附属预览标签 | 编译后的 PDF 手稿本身即为工作台，需要时可随时展开源码对照 |
| 向 AI 表达修改意图 | 复制代码段到对话栏，或在 `.tex` 光标处提问 | 指定文件路径、行号范围或框选源码片段发给智能体 | 直接在 PDF 页面高亮句子或框选公式、图表写批注，SyncTeX 自动定位源码行 |
| 审阅 AI 的修改结果 | 查看源码变动，或重编译后在整份新 PDF 中人工寻找差异 | 基于文本行的红绿 `git diff` 原始标记语言补丁 | 在页面原位展示排版后的修改前后对比（含渲染好的公式与表格），支持单条批注备选方案与源码切换 |
| 多人协作方式 | 浏览器原生多人实时光标同步，分享链接即可加入 | 依赖 Git 推送与拉取；若合作者只用 Overleaf 则容易脱节 | 内置 Git 工作树隔离任务，**同时支持与 Overleaf 约 1 秒双向实时同步** |
| 智能体与模型选择 | 绑定平台自身提供的内置助手选项 | 通常绑定单一 IDE 厂商，或每次手动切换单一 CLI 工具 | 自带账号或密钥使用全部 16 种智能体：内置 Papilot Writer 与 15 种编程智能体（Codex、Claude、Cursor、Copilot、Antigravity、Pi、OpenCode 等） |
| 运行条件、文件与许可 | 云端托管项目，本机免装 TeX 环境 | 本地纯文本文件 + Git + 本地 TeX 发行版 | 本地纯文本文件 + Git + 本地 TeX 发行版；MIT 协议免费开源 |

## 不必说服合作者迁移：与 Overleaf 实时双向同步

很多研究者对本地工具望而却步，真正的原因往往不是功能，而是一句非常现实的顾虑：“我的导师和另外三位合作者都在 Overleaf 上改稿。”如果把项目导出成 ZIP 在本地让 AI 修改，再把 `.tex` 文件粘贴回网页，几乎不可避免地会覆盖合作者刚刚写下的段落。

从 Papilot 0.11 开始，**与 Overleaf 同步（Sync with Overleaf）** 直接消除了这道二选一的门槛。你可以粘贴 Overleaf 项目链接或带编辑权限的分享链接直接导入，也可以把已有的本地稿件关联到对应的 Overleaf 项目。运行期间，本地文件夹与远端项目通过 Overleaf 的实时编辑服务保持同步：

- **约 1 秒双向送达。** 你在 Papilot 中审阅接受并应用到稿件的修改，约 1 秒内就会出现在合作者的 Overleaf 浏览器窗口里；对方在网页上的输入也会实时写回你的本地 `.tex` 文件并更新 PDF。
- **同段并发逐字合并。** 当双方恰好在同一段落同时编辑时，改动会像两个 Overleaf 网页窗口之间那样按字符合并，而不会整文件互相覆盖。
- **普通免费账号即可使用，且不污染共享稿件。** 同步无需开通 Overleaf 付费 Git 功能（同样支持自建 Overleaf 实例）；而 AI 智能体的每次尝试依然隔离在本地独立的 Git 工作树中，在你逐处审阅点击“应用”之前，绝不会把未经核实的半成品直接推给合作者。

![Papilot 产品示意图：展示论文页面原位的修改前后排版对比，以及接受、拒绝和评论操作。](/assets/blog/review.zh-CN.png "在将改动同步给 Overleaf 上的合作者之前，先在本地页面上逐处审阅排版后的修改前后对比。")

项目的起步同样顺畅：在 **导入或打开** 面板中粘贴 arXiv 论文链接、Overleaf 分享链接或公开 GitHub 仓库地址，Papilot 会自动识别主文档与编译引擎；如果是新建文稿，[Papilot Universe](https://papilot.ai/universe/) 提供了涵盖 400 多个学术会议以及期刊、学位论文、幻灯片、海报、简历与书籍的开箱即用模板。

## 按写作阶段选择合适的工具组合

因为 Papilot 底层操作的就是磁盘上标准的 `.tex` 与 `.bib` 纯文本文件，这三种工具在真实科研生活里完全可以各司其职：

1. **只打开浏览器用 Overleaf**：当你临时在没有配置 TeX 环境的电脑或平板上查看项目、随手改几个拼写错误，或是邀请不打算配置本地环境的合作者共同编辑时，网页端依然最轻便。
2. **切回本地源码 IDE**：当你正在从零编写自定义 `.cls`/`.sty` 宏包、排查底层宏展开报错，或用脚本批量生成实验数据宏文件时，纯代码编辑器最直接。
3. **以 Papilot 为主工作台**：当你进入正文撰写、结构重写、公式核查与多轮改稿阶段——直接在成稿 PDF 上指认问题，逐处审阅排版后的修改前后对比，让 AI 处理繁琐的标记语言，而把学术判断稳稳留在自己手里。

在配置本地环境之前，你可以直接在浏览器里打开免安装的[交互式在线演示](/demo/)，亲手体验在 PDF 上批注和逐条审阅排版差异的完整闭环。如果这套工作流契合你的写稿习惯，欢迎前往 [papilot.ai](/zh-CN/) 下载 macOS、Windows 或 Linux 客户端，也欢迎在 [GitHub 上为 Papilot 点一颗 Star](https://github.com/PapilotAI/papilot)，方便下一篇截稿日前随时取用。
