LaTeX으로 논문을 쓰는 연구팀이라면 결국 도구 선택에서 저마다 조용한 타협점에 이르곤 합니다. 어떤 공저자는 수 기가바이트짜리 TeX 배포판을 설치하지 않고도 브라우저 탭만 열면 어디서든 원고를 고칠 수 있는 환경을 선호하고, 또 다른 공저자는 Git과 단축키, 코딩 에이전트를 연결한 로컬 코드 편집기 안에서 살아갑니다. 그리고 누군가는 늘 컴파일된 PDF를 내보내 태블릿이나 전체 화면 리더로 통독합니다. 실제로 조판된 지면을 마주해야만 매끄럽지 못한 문단 전환이나 빽빽하게 들어찬 표, 슬그머니 잘못 적힌 첨자와 표기가 비로소 눈에 들어오기 때문입니다.

오늘날 'AI 기반 LaTeX 집필 도구'를 찾는 연구자들에게 부족한 것은 더 이상 똑똑한 언어 모델이 아닙니다. 주류 코딩 에이전트는 이미 여러 파일을 넘나들며 사용자 정의 매크로를 추적하고, `.bib` 참고문헌 항목을 정리하며, 복잡한 수식을 다시 짜는 일까지 거뜬히 해냅니다. 일상적인 퇴고의 품질을 좌우하는 진짜 핵심은 에이전트를 둘러싼 **작업 공간의 계약**입니다. 어디에서 고쳐야 할 문제를 짚어내고, AI가 수정한 결과를 무엇으로 검증하며, 더 손에 익는 도구를 도입했을 때 공저자들에게까지 이전을 강요하게 되는지 여부가 바로 그것입니다.

어느 한 도구가 모든 상황에서 다른 도구를 완전히 대체한다고 주장하기보다, 현재 가장 널리 쓰이는 세 가지 LaTeX 워크플로—Overleaf로 대표되는 브라우저 분할 화면 편집기, 코딩 에이전트를 결합한 로컬 소스 IDE, 그리고 완성본 PDF를 중심에 둔 [Papilot](https://github.com/PapilotAI/papilot) 작업 공간—를 나란히 놓고 객관적으로 비교해 보고, 실시간 동기화를 통해 같은 원고 위에서 어떻게 매끄럽게 호흡을 맞출 수 있는지 살펴보겠습니다.

## 기존 LaTeX 워크플로가 제대로 해결한 것들

소스 코드 중심의 AI 편집이 어디에서 병목을 겪는지 짚어 보기 전에, Overleaf와 로컬 코드 편집기가 왜 학술 집필의 주류로 자리 잡았는지 먼저 인정할 필요가 있습니다.

**Overleaf는 공동 집필의 진입 장벽을 허물었습니다.** 웹 기반 TeX 편집기가 보급되기 전에는 여러 기관의 연구자들이 함께 논문 한 편을 쓰려면 초록을 한 줄 적기도 전에 서로 다른 TeX Live 연도 버전, 누락된 `.sty` 패키지, Git 병합 충돌부터 해결해야 했습니다. 링크 하나만 공유하면 모두가 브라우저에서 동시에 타이핑하며 글자 단위로 움직이는 서로의 커서를 즉시 볼 수 있는 방식은, 기술적 배경이 다른 공저자들이 별도 설정 없이 한 원고에 합류하는 가장 간편한 방법으로 여전히 자리매김하고 있습니다. 특히 로컬 TeX 환경이 설치되지 않은 기기에서 작업할 때 진가를 발휘합니다.

**로컬 소스 IDE는 저장소 규모와 자동화를 해결했습니다.** VS Code와 LaTeX Workshop, 혹은 Cursor나 Neovim에 Claude Code, Codex 같은 터미널 에이전트를 결합해 로컬 Git 저장소에서 작업하면 빠른 다중 파일 검색, 오프라인 `latexmk` 컴파일, 재현 가능한 도표 생성 스크립트는 물론 `.cls` 문서 클래스나 `.sty` 패키지, 프로그래밍 방식의 TikZ 그림을 직접 작성할 때 세밀한 소스 제어력을 얻을 수 있습니다.

그러나 이 두 워크플로는 똑같은 지점에서 뚜렷한 마찰에 부딪힙니다. 바로 **본문의 논증과 수학적 유도 과정에 AI가 가한 실질적인 수정을 검토하는 단계**입니다.

![세 가지 LaTeX 워크플로의 나란히 비교: Overleaf 브라우저 분할 화면, 코딩 에이전트를 결합한 로컬 소스 IDE, 그리고 실시간 Overleaf 동기화를 지원하는 Papilot의 PDF 중심 작업 공간.](/assets/blog/three-workflows.ko.svg "Overleaf는 설치 없는 웹 공동 편집에, 소스 IDE는 날것의 마크업 편집에 강점이 있습니다. Papilot은 AI 주석과 수정 검토를 렌더링된 PDF 위로 옮겨 오며 실시간 동기화로 Overleaf와 연결됩니다.")

브라우저 분할 화면이든 코드 IDE든, AI 어시스턴트가 고치는 대상은 `.tex` 마크업이며 저자에게 가장 먼저 돌려주는 결과물도 붉은색과 초록색이 뒤섞인 소스 코드 diff입니다. 줄바꿈이 다시 정리된 긴 영문 문단이나 프로젝트 고유 매크로가 얽힌 여러 줄짜리 `\begin{align}` 유도식 앞에서 코드 패치를 읽는다는 것은, 저자가 머릿속으로 LaTeX을 직접 컴파일해야 함을 뜻합니다. 설령 전체 PDF를 다시 컴파일하더라도 새 PDF가 아홉 번째 페이지에서 어떤 기호 몇 개가 미묘하게 바뀌었는지 스스로 표시해 주지는 않으므로, 결국 신구 판본 사이를 눈으로 번갈아 대조하며 찾아내야 합니다.

## 공저자에게 이전을 강요하지 않는 협업: 실시간 양방향 Overleaf 동기화

많은 연구자가 로컬 LaTeX 도구 도입을 망설이는 가장 흔한 이유는 기능 때문이 아니라 지극히 현실적인 한마디 때문입니다. *"지도교수님과 다른 공저자 세 명이 이미 Overleaf에서 원고를 고치고 있어요."* 프로젝트를 ZIP으로 내려받아 로컬에서 AI로 수정한 뒤 바뀐 `.tex` 파일을 다시 브라우저 탭에 붙여넣다 보면, 공저자가 방금 작성한 문단을 덮어쓰는 일이 순식간에 벌어집니다.

Papilot 0.11부터 도입된 **Overleaf와 동기화**(Sync with Overleaf)는 이러한 양자택일의 부담을 없애 줍니다. Overleaf 프로젝트 링크나 편집 권한이 켜진 공유 링크를 Papilot에 바로 붙여넣어 가져올 수도 있고, 기존 로컬 원고 폴더를 해당 Overleaf 프로젝트에 연결할 수도 있습니다. 실행 중에는 Overleaf의 실시간 편집 서비스를 통해 로컬 파일과 원격 프로젝트가 발맞추어 동기화됩니다.

- **약 1초 내외의 양방향 실시간 반영.** Papilot에서 검토 후 수락하여 원고에 적용한 변경 사항은 약 1초 안에 공저자의 Overleaf 브라우저 탭에 나타나며, 상대방이 웹에서 입력한 내용도 로컬 `.tex` 파일과 컴파일된 PDF에 실시간으로 반영됩니다.
- **동일 문단 동시 편집 시 글자 단위 병합.** 양쪽에서 같은 순간에 같은 문단을 고치더라도 두 개의 Overleaf 브라우저 탭 사이에서와 마찬가지로 글자 단위로 병합되므로 파일 전체를 덮어쓰지 않습니다.
- **유료 Git 부가 기능 없이 무료 계정으로 사용 가능하며 공유 원고를 안전하게 보호.** 동기화는 Overleaf 유료 Git 기능을 결제할 필요 없이 일반 무료 계정으로 작동하며(자체 호스팅 Overleaf 인스턴스도 지원), AI 에이전트의 각 시도는 로컬의 독립된 Git 워크트리에 격리되므로 직접 곳곳을 검토하고 '적용'을 누르기 전까지는 검증되지 않은 초안이 공저자에게 넘어가지 않습니다.

![논문 페이지 제자리에서 조판된 수정 전후 비교와 수락, 거절, 코멘트 동작을 보여 주는 Papilot 제품 화면 예시.](/assets/blog/review.en.png "공유 중인 Overleaf 프로젝트에 변경 사항을 반영하기 전에, 로컬 페이지 위에서 AI가 제안한 모든 수정을 조판된 전후 비교로 하나씩 검토합니다.")

원고를 작업 공간으로 불러오는 시작 과정도 간결합니다. '**가져오기 또는 열기**' 패널에 arXiv 논문 URL(초록, PDF, HTML 링크), Overleaf 보기·편집 링크, 또는 공개 GitHub 저장소 주소를 붙여넣으면 메인 `.tex` 엔트리 파일과 컴파일러 엔진을 자동으로 감지합니다. 백지에서 새로 시작할 때는 [Papilot Universe](https://papilot.ai/universe/)에서 400개 이상의 학술대회를 비롯해 저널, 학위논문, 슬라이드, 포스터, 이력서, 도서용 템플릿을 바로 컴파일해 사용할 수 있습니다.

## 논문의 집필 단계에 맞춰 알맞은 도구 조합하기

Papilot은 디스크 위의 표준 `.tex` 및 `.bib` 플레인 텍스트 파일을 그대로 다루기 때문에, 세 가지 워크플로는 서로 배타적이지 않으며 실제 연구 과정 속에서 자연스럽게 역할을 나눌 수 있습니다.

1. **브라우저에서 Overleaf만 열 때**: TeX가 설치되지 않은 외부 컴퓨터나 태블릿에서 잠시 프로젝트를 확인하고, 빌린 노트북에서 가벼운 오타나 문구를 손보거나, 로컬 환경 설정을 원치 않는 공저자를 초대해 함께 편집할 때는 웹 환경이 가장 가볍습니다.
2. **로컬 소스 IDE를 열 때**: 자체 `.cls`/`.sty` 스타일 파일을 처음부터 설계하거나 저수준 매크로 확장 오류를 디버깅할 때, 또는 Python이나 R 스크립트로 실험 데이터 `.tex` 표를 일괄 생성하는 파이프라인을 짤 때는 순수 코드 편집기가 가장 직관적입니다.
3. **Papilot을 주 작업대로 삼을 때**: 본문 집필, 논증 구조 재편, 수식 유도 검증, 그리고 AI 에이전트와 함께 여러 차례 퇴고를 거듭하는 단계에서는 조판된 페이지 위에서 문제를 바로 짚어내고 제안된 모든 변경을 렌더링된 수정 전후 PDF 비교로 검토함으로써, 학술적 판단력을 예리하게 유지하면서도 명시적으로 적용하기 전까지 공유 원고를 안전하게 지킬 수 있습니다.

로컬 TeX 환경이나 모델을 설정하기 전에 브라우저에서 설치 없이 바로 열 수 있는 [대화형 데모](/demo/)를 통해 PDF 주석 작성과 조판 차분 검토 루프를 직접 체험해 보세요. 이 워크플로가 여러분의 논문 집필 방식에 잘 맞는다면 [papilot.ai](/ko/)에서 macOS, Windows, Linux용 데스크톱 앱을 다운로드하고, 다음 마감일 전에 언제든 다시 찾을 수 있도록 [GitHub에서 Papilot에 스타를 눌러 주세요](https://github.com/PapilotAI/papilot).
